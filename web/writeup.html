The best bits of DOPE's assembly

Seventeen snippets, disassembled with ndisasm -b16 from the unpacked blocks. Addresses are offsets inside the unpacked block. The listings are the real bytes; the explanations are my reading of them, and I say where that is a guess.

Part 1 is block 1; the texture loop and projection are in block 2. Block 2's own banner says it all: "DON'T TELL ME IT'S NOT OPTIMIZED OR 'REAL' BECAUSE I KNOW THAT ALREADY! WHY OPTIMIZE ANYTHING FOR PENTIUM 100 MHZ?" It is optimised anyway.

1. Wait for the retrace edge, not for "a" retrace

0110  mov dx,0x3da
0113  in  al,dx
0114  test al,8
0116  jnz 0x113        ; first: leave any retrace already in progress
0118  in  al,dx
0119  test al,8
011B  jz  0x118        ; then: wait for the next one to begin
011D  ret

Waiting only for "bit 3 set" returns immediately if you are halfway through a retrace, and the palette write that follows then lands in the visible picture. Two loops, nine instructions, and every caller starts at the leading edge. It is called around mode switches and during timer calibration.

2. A timer interrupt that keeps the DOS clock right using the carry flag

015A  call 0xc24            ; rewrite the palette
015D  mov ax,[cs:4]         ; PIT reload value we programmed
0161  add [cs:6],ax         ; 16-bit accumulator of PIT counts  -> CF
0166  popad
0168  pop gs
016A  pop fs
016C  pop es
016D  pop ds                ; none of these touch the flags
016E  jc  0x171
0170  iret
0171  jmp far [cs:0]        ; chain to the original INT 8 (BIOS clock)

The demo drives the PIT at its own rate (about once per video frame, see 3), so the BIOS tick that updates the DOS time would run far too often. Instead of counting, the handler adds the reload value into a 16-bit accumulator. The accumulator wraps once per 65,536 PIT counts, which is exactly the BIOS's native 18.2 Hz period, and when it wraps the carry flag is set. The handler then pops a dozen registers and still branches on that carry, because pop and popad don't modify flags. One add is the whole bookkeeping, one jc decides whether to chain. The DOS clock stays correct even though the interrupt rate was changed.

3. Calibrating the timer against the monitor, with one multiply

01D6  call 0x110            ; sync to retrace
01D9  mov al,0x36 / out 0x43,al ; count 0 = 65536 free-running
...   xor al,al / out 0x40,al / out 0x40,al
01E7  call 0x110            ; one whole frame later
01EF  xor eax,eax / out 0x43,al      ; latch counter
01F6  in al,0x40 / mov ah,al / in al,0x40 / xchg al,ah
0200  neg ax                ; down-counter: elapsed = -count
0206  imul eax,eax,0x3de
020D  shr eax,11            ; x 990/2048, about 0.483
0211  mov [cs:4],ax

The code measures how many PIT counts one vertical retrace period takes on this monitor (about 17,000 at 70 Hz), then scales it by 990/2048 with a multiply and a shift: no division, and a power-of-two divisor. That number becomes the one-shot reload (mode 0x30) that the handler in snippet 2 re-arms after waiting for retrace. My reading: the interrupt fires a little under half a frame after retrace begins, so the scroll registers are written at a fixed point in the frame regardless of monitor refresh rate. That's inference from the constants; the measured rate on the running demo is 69 interrupts/s.

4. A 64-entry gradient from a fixed-point accumulator that saturates by skipping

0C00  test dx,dx
0C02  jns 0xc06
0C04  xor dx,dx              ; negative step -> 0
0C06  shr dx,4
0C09  cmp dx,0x100
0C0D  jc  0xc12
0C0F  mov dx,0x100           ; clamp the step
0C12  mov cx,0x40
0C15  mov [cs:bx],ah         ; store the integer part, free: AH is bits 8..15
0C18  inc bx
0C19  cmp ax,0x3f00
0C1C  ja  0xc20              ; already at 63.x: stop adding
0C1E  add ax,dx
0C20  dec cx
0C21  jnz 0xc15

AX is an 8.8 fixed-point number, so ah is the integer part, no shift needed. The saturation at 63 (the DAC is 6 bits) is done by not adding when AX is already above 0x3f00, instead of clamping the result afterwards. The step comes from the demo's counter, so the ramp's slope, and with it the palette crossfade in part 1, moves with time with no per-frame float code at all.

5. Palette crossfade: 64 colours are 192 bytes, treat them as 192 bytes

0C2A  mov cx,0xc0
0C2D  mov dx,0x3c8 / xor al,al / out dx,al / inc dx   ; DAC write index 0, then port 3C9
0C34  mov bl,[cs:bp+0x4f0]     ; index into ramp A
0C39  mov al,[cs:bx+0x16c]
0C3E  mov bl,[cs:bp+0x7f8]     ; index into ramp B
0C43  add al,[cs:bx+0x1ac]
0C48  cmp al,0x3f
0C4A  jc  0xc4e
0C4C  mov al,0x3f              ; saturate
0C4E  mov [cs:bp+0x1ec],al     ; shadow copy
0C53  inc bp
0C54  out dx,al                ; DAC auto-increments R,G,B,R,G,B...
0C55  dec cx
0C56  jnz 0xc34

There is no "colour" structure here. The loop runs 0xC0 = 192 times and streams one byte per iteration into port 0x3C9; the VGA DAC auto-increments through R, G, B and then to the next entry, so no code separates the components. Each byte is a saturating sum of two ramp entries chosen by two precomputed index tables (one for each of the two ramps from snippet 4). Changing the two ramps' slopes crossfades two whole palettes while the picture itself is never touched: the effect costs 192 table lookups per frame. In the JS port this is clamp(rampA[tblA[i]] + rampB[tblB[i]], 63) and it matches the original frames.

6. Unpacking a picture into planar VRAM, four pixels per store

0C5C  push ds
0C5D  mov cx,0xc3            ; 195 rows
0C60  push cx
0C61  mov cx,0x40            ; 64 groups per row
0C64  mov bl,[si+8]
0C67  mov bh,[si+0xc]
0C6A  shl ebx,16
0C6E  mov bl,[si]
0C70  mov bh,[si+4]
0C73  mov [es:di],ebx        ; ONE 32-bit store
0C77  mov bx,ds
0C79  inc bx
0C7A  mov ds,bx              ; source += 16 bytes, via the segment register
0C7C  add di,4
0C7F  dec cx
0C80  jnz 0xc64

Two tricks. First, the VGA is in an unchained planar mode, so pixel x lives in plane x mod 4. For one plane the pixels sit in the source at stride 4: [si], [si+4], [si+8], [si+0xc]. Gathering those four bytes into ebx with the 16-bit halves trick (shl ebx,16 to make room) lets a single mov [es:di],ebx write four consecutive plane bytes; the map mask register selects the plane, and the whole picture is four passes. Second, the source pointer advance is inc ds, a 16-byte step, instead of add si,16: the 213 KB picture strip is bigger than a 64 KB segment, and moving the segment instead of the offset means the offset never overflows. This is also why the picture has to be placed where the loader mapped it.

I only understood this snippet after the first port was wrong by a units error: the card's plane bytes cover four pixels each, and the CRTC start/offset registers count plane bytes. Once that was right the frames matched exactly.

7. The scroll: two register writes from one counter

0C8D  mov bx,[cs:0x16a]       ; the shared counter
0C92  shr bx,4                ; 16 counts = one start-address unit
0C95  mov dx,0x3d4
0C98  mov al,0xc / mov ah,bh / out dx,ax     ; CRTC start high
0C9D  inc al / mov ah,bl / out dx,ax         ; CRTC start low
...
0CAF  mov ax,[cs:0x16a]
0CB3  shr ax,2 / and al,3 / add al,al        ; pixel pan 0,2,4,6 (bits 1..2)
0CBA  out dx,al               ; attribute controller 0x33, horizontal pan

Each out dx,ax writes the index byte and the data byte with one instruction (the CRTC and sequencer are 16-bit friendly: index at port N, data at N+1). The scroll is the same counter read twice: its high bits move the CRTC start address in coarse steps, its low bits go to the attribute controller's pixel panning register for the fine steps, so the picture appears to scroll one pixel at a time through a register that can only move four. No pixel is ever copied; the whole "animation" of part 1 is a window moving over an unpacked image, which is why the port can draw it as a crop.

8. Texture mapper inner loop: 14 instructions per pixel, self-modifying

27C0  mov edx,[cs:0x2650]     ; setup: V accumulator
27C6  ; --- loop body, per pixel ---
      mov bl,ch
      shld ebx,ecx,9
      and  bx,0x7f7f          ; both coordinates wrapped to 128 with one AND
      inc  di
      mov  al,[fs:bx]         ; lookup 1 (a map in segment FS)
      shld ebx,edx,8
      mov  si,[cs:eax*2+0]    ; table of row offsets, 32-bit index in 16-bit code
      mov  bh,dh
      add  ecx,0              ; immediate is patched at runtime
      mov  bl,[bx+si]         ; lookup 2 (segment DS), shaded by SI
      add  edx,0              ; patched too
      mov  [es:di-1],bl
      inc  bp
      jnz  loop               ; BP counts up from negative to 0

(Block 2, loop body 0x27C6..0x27FA, preceded by its setup.) Things worth noticing:

  • Self-modifying code. add ecx,0 and add edx,0 encode a 32-bit immediate of zero in the file. These are placeholders: the per-polygon texture gradients are written into the instruction stream before the span loop runs, so the deltas live in the instruction instead of occupying registers. On a 486/Pentium that frees two registers in a loop that wants all of them.
  • No compare. The span length is sub bp,dx (negative); inc bp / jnz counts it up to zero, and the jns before the loop skips empty spans.
  • shld as a bit packer. It shifts bits from one register into another, so the two fixed-point coordinates are assembled into one index register with no shl/or pairs; and bx,0x7f7f then wraps both halves at once.
  • A 32-bit address in a 16-bit segment: mov si,[cs:eax*2+0] carries the 0x67 prefix. The "+0" displacement is another patched address.
  • Segments as free pointer registers: fs, ds, es and cs each address a different table or buffer, so the loop needs no base-register arithmetic.

The segment registers are not an accident: ds and fs are loaded from two four-entry tables at cs:0x400 and cs:0x408 indexed by the sub-pixel phase of the span start, i.e. one texture/shading pair per pixel phase. The values are block-relative constants that the loader relocates (it adds the part's base segment to them), like part 1's push 0xe4. Measured: the first pair is 0x6538/0x6540 in the block, +0xf7b in memory = 0x74b3/0x74bb, and 0x74b3:0 is block 0x65380 -- a 128x128 map of palette indices 1..127, the blue environment map the credits discs are textured with. 0x6540 is eight paragraphs (128 bytes) later, so the second lookup is the same map shifted by a row; that is what draws the fine horizontal dither, not a separate shade image. (An earlier note here guessed the map at block 0x35270; that is the gradient builder's output, not this texture.)

9. A part that never needed a per-line palette

1B21  cli
1B22  push ax / push dx
1B24  mov al,0x20 / out 0x20,al     ; EOI
1B28  inc word [cs:0x1a1f]          ; tick counter
1B2D  mov dx,0x3da / in al,dx
1B31  test al,8 / jz 0x1b30         ; wait for the START of vertical retrace
1B35  mov dx,[cs:0x1a05]            ; calibrated divisor
1B3A  mov al,0x30 / out 0x43,al / out 0x40,al / out 0x40,ah
1B47  call far [cs:0x1a09]          ; the frame hook
1B4C  mov ax,[cs:0x1a05]
1B50  add [cs:0x1a07],ax            ; carry = a BIOS tick is due
1B57  jc 0x1b5a / iret              ; chain to the old handler only then
268B  mov ax,[cs:0x1957] / add [cs:0x1955],ax   ; a bounce offset
26AB  cmp word [cs:0x193f],1 / jnz 0x26f6      ; fade running?
26B3  mov ax,[cs:0x1941]
26CA  add word [cs:0x1941],0xff               ; 64 steps to the top
26D1  mov dx,0x100 / mov bx,0x2510 / call 0x2650   ; rebuild the 64 entry ramp
26DA  xor bx,bx / mov si,0x1f10 / mov cx,0x300
26E2  mov dx,0x3c8 / xor al,al / out dx,al
26E9  mov bl,[cs:si] / mov al,[cs:bx+0x2510] / out dx,al
26F3  loop 0x26e9                 ; 768 DAC bytes, through the ramp
2738  inc dword [cs:0x1924] / inc dword [cs:0x1928]

This is the whole colour side of part 2: all 256 DAC entries, rewritten in one go from a fixed base palette, each byte passed through a 64 entry brightness table that ramps up to the identity over 64 ticks. The interrupt waits for the start of vertical retrace before it does it, so the palette changes between frames and not inside one. The two lessons here:

  • Count the entries before believing in mid-frame palette tricks. These frames hold 70..107 colours, which a 192 entry part 1 palette cannot explain but a 256 entry palette explains trivially. Every colour of all ten reference frames comes out of the base palette at ramp step 0x100, which is what retired the earlier "per line palette" reading (tests/test_part2.mjs).
  • The fade is a table lookup on the palette, not on the picture. 768 bytes of out per tick is cheap on a 486; retouching the screen would not have been.

10. Sorting polygons by splitting the list at both ends of one buffer

; block 2, 0x369a
369A  mov edx,0x40000         ; the flag bit that decides the side
36A0  mov si,0x0              ; read from the front of the input
36A3  mov di,0x1450           ; "low" list grows upward from here
36A6  mov bx,[cs:0x1906]      ; "high" list grows downward from the end
36AB  jmp 0x36b2
36AD  mov [di],eax            ; flag clear: append to the low list
36B0  add di,bp               ; bp = 4
36B2  mov eax,[si]
36B5  test ax,ax
36B7  js  0x36d0              ; a negative low word ends the list
36B9  add si,bp
36BB  test edx,eax
36BE  jz  0x36ad
36C0  mov [bx],eax            ; flag set: push on the high list
36C3  sub bx,bp
36C5  jmp 0x36b2
...
36DF  mov eax,[di]            ; then copy the low list back, and the high list
36F0  mov eax,[bx]            ; after it, walking it backwards

One pass over a list of 32-bit records (depth << 16 | polygon index) puts the records with a flag bit set at one end of a scratch buffer and the others at the other end, then writes both back, the second one in reverse. That is a one-bit radix partition done with two stacks that grow towards each other, no counters and no second buffer. The terminator is any record whose low word is negative, so the loop needs no count either. It has a limit nobody wrote down. In part 6's copy of the routine (block 0x2dea) the input starts at 0x3200 and the scratch area at 0x41a0, 1000 records further, so a longer list overwrites its own tail. I found out because a seek that fed part 6 its timer interrupts too fast made the frame in progress see a scene with 1,183 visible faces, and the sorter then walked off the end of memory for ever.

11. Patching the immediates of your own loop

2800  add dword [cs:0x2650],0x0    ; imm32 filled in at run time
293F  add ebp,0x0                   ; "
2946  adc edx,0x0                   ; "
28E6  mov bl,ch                     ; ... the span loop at 0x27c6 / 0x28e6 has
2905  add ecx,[cs:0x26e8]           ; the same deltas as memory operands

The per-polygon edge and texture gradients are not kept in registers or variables: before a polygon is drawn the setup writes them straight into the immediate fields of the add instructions that will consume them (the zeros in the file are placeholders). Three or four such fields exist per part, and the polygon filler runs thousands of times per frame. It saves a register or a memory read per use on a CPU with eight registers, and costs a pipeline flush on Pentiums; the authors accept that, and wrote a second loop at 0x28e6 with the deltas as [cs:...] operands for the clipped case. For the recompiler on this page it is the one thing that breaks the usual assumption that code is constant: it marks every translated byte, drops a block when a store hits it, and after the first hit on an immediate reads that field from memory when the block runs. Without that, part 2 recompiled its span loop 112,000 times in 3 seconds.

12. Division that looks like cdq and is cwd

; block 5, 0x1fb4: bytes  A1 46 23  2B 06 3E 23  99  F7 FB
1FB4  mov ax,[0x2346]
1FB7  sub ax,[0x233e]         ; difference of two 16 bit lanes
1FBB  cwd                     ; 99, no 66 prefix: dx = sign of AX
1FBC  idiv bx                 ; DX:AX / dy, the lane's slope per row

The texture-gradient setup divides four 16 bit differences by the number of rows, and the instruction in between is the single byte 99. In 16 bit code that is cwd; with a 66 prefix it is cdq, and a few lines later the code does use 66 99 (shl eax,16 / cdq / idiv ebp) for the 32 bit gradient. The disassembler I used prints both as cdq. A port that believes it extends the sign of the whole of eax has a dividend whose upper half depends on whatever eax held from the previous division, and a negative difference gets divided as a large positive number. The first version of the part 5 port did exactly that; the polygon-by-polygon check found it, as a row slope that differed in one lane of one triangle. Check the bytes whenever the high half of a register is involved.

13. A shift of 10 where a shift of 8 was meant

; block 3, 0x2158 (phong index)         ; block 5, 0x1c98
mov bl,ch                              mov bl,ch
shld ebx,ecx,8                         shld ebx,ecx,0xa      ; 66 0F A4 CB 0A
and bx,0x7f7f                          and bx,0x7f7f
mov al,[fs:bx]                         mov al,[fs:bx]

The phong fill packs two 16 bit coordinates in one register and looks up a 128 x 128 map with the top seven bits of each. With a shift of 8 the high byte of ecx lands in bl and the previous bl (the other coordinate's high byte) in bh: a clean (y,x). Parts 5 and 6 shift by 10, part 2 by 9. Shifting by 10 pushes bl up by ten places, so only its low six bits survive, in bits 10 to 15, and the low byte is made of bits 22 to 31 of ecx: the index mixes the two coordinates. Nobody would write that on purpose, but it is what parts 5 and 6 look like, and a port that "fixes" it to 8 is wrong in one pixel out of a few thousand: it was found in frame 883 of 2,253.

14. The rounding the matrix routine lost

; block 2, 0x1f05 (66 C1 F8 0F  66 83 D0 00)         ; block 3, 0x1f71
sar eax,0xf                                           sar eax,0xf
adc eax,0x0                 ; + the bit shifted out         ; (nothing)

Part 2's rotation matrix is built with fifteen bit fixed point multiplies, and after every sar eax,15 an adc eax,0 adds the last bit shifted out: round to nearest instead of truncate. The other four parts' copies of the same routine have lost every one of those adcs. In part 2's own copy the author forgot one (the inner product of the fourth entry, sar ebx,0xf straight into imul ebx,[0x1d58]), and the port has to forget it as well. I only learned that the routine was there because a variable that the picture never reads differed by one.

15. A lighting table that breathes: the ramp built with lea and neg

; block 5, 0x3199, called by the timer every tick with dx = brightness
3199  lea bx,[edx*8]          ; bx = 8 * dx
31A1  neg bx                  ; ... negated
31A3  mov cl,0x10
31A8  mov [cs:si],bh          ; ramp[k] = high byte of ((k - 8) * dx)
31AC  add bx,dx
...
31BA  mov ah,[cs:di]          ; table[16*i + j] = ramp[i] << 8 | ramp[j]
31C2  mov al,[cs:si]

The phong fill reads a row offset out of a 256 word table. In part 3 it is a constant. In parts 5 and 6 the timer interrupt rebuilds it every tick from a single number (dx, from the sine of a running angle): a 16 entry ramp centred on zero, ((k - 8) * dx) >> 8, built without a multiply by negating 8 * dx and adding dx sixteen times, then every pair of entries makes a word. The effect is that the lit sphere the surface is shaded from gets bigger and smaller, 70 times a second, for the price of 16 bytes and 256 stores per tick.

16. A recursive blur by table lookup

; block 2, 0x3780: the whole screen, two pixels per iteration
3780  mov bh,[si]              ; what this pixel was last frame
3782  mov bl,[es:si]           ; what the polygons drew now
3785  mov dl,[fs:bx]           ; out = shade[old << 8 | new]
...
1AAB  imul ax,ax,0x1a0         ; the table: (0x1a0 * old + 0x60 * band) / 2 / 256
1AB6  or ah,0x80

Part 2 has no clear and no averaging loop. The polygons are drawn on a band buffer, and a 64 KB table indexed by (previous output, band pixel) gives the new output: 0x1a0/512 = 81 % of the old value plus 0x60/512 = 19 % of the new one. Writing the result back into the same buffer makes it a feedback filter: moving shapes leave a soft glow behind them. The table is built three times over ([bx+0x80], [bx-0x8000], [bx-0x7f80]) so the high bit the output always carries is ignored by the next lookup. One step of the script zeroes half of the table, which cuts the feedback and makes the next frames dark. Per pixel it costs two loads, a table lookup and a store.

17. A pixel loop that counts in al

; block 7, 0x2a51 (the clipped texture span) - the same shape in blocks 2, 5, 6
2A51  shld ebx,ecx,8
2A56  mov bh,ch
2A58  add ecx,ebp              ; both texture coordinates in one add
2A5B  mov ah,[fs:bx]
2A5E  mov [es:si],ah
2A61  inc si
2A62  dec al                   ; only the low byte of the count
2A64  jne 0x2a51

Eight instructions per textured pixel, with the two 16 bit texture coordinates added by one add ecx,ebp and the pixel read through fs:bx. The pixel count is in ax but the loop tests al. A span of 256 pixels or more therefore draws its length modulo 256, and a span of exactly 256 draws 256 (because dec al from zero wraps). A span that long is rare on a 320 pixel screen, so the original gets away with it; the port keeps the quirk.

Bonus: projection with the rounding folded into the centre offset

1E04  sar eax,3
1E08  adc ax,0xa0           ; x = X*f/z / 8 + 160, rounded
...
1E1C  lea eax,[eax+eax*2]   ; y * 3
1E21  sar eax,5
1E25  adc ax,0x64           ; y = Y*f/z * 3/32 + 100, rounded

sar pushes the last shifted-out bit into the carry flag; adc then adds the screen-centre constant and that bit in one instruction. That is round-to-nearest for free. The y line multiplies by 3 with lea and shifts by 5, so y is scaled by 3/32 against x's 1/8 = 4/32: a 4:3 ratio between horizontal and vertical scale built into the projection. Whether that was a deliberate correction for mode 13h's non-square pixels (a pure correction would be 5:6) or a matter of taste I can't say from the code, but it is one more reason to display this demo at 4:3.

The dividend is signed: imul eax,[cs:0x191c] produces a negative 64 bit product in EDX:EAX for a vertex in front of the camera, and idiv ebp divides the sign-extended pair. That detail cost this port a lot of time: the verification rig first combined EDX:EAX as unsigned, so the quotient came out ~232 times too large, the span fill ran for 64 K pixels, and one part 2 frame looked like 3.5×108 instructions. With the signed pair (tests/test_x86.mjs) the same frame is 1.4×106. The bytes at block 0x1dfc are 66 A1 50 1B 66 F7 2E 1C 19 66 F7 FD.
