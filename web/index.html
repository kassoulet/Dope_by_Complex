DOPE by Complex (The Gathering 1995)

A 1995 MS-DOS demo, taken apart and put back together in JavaScript. Part 1 is read out of the original DOPE.EXE, parts 2 to 7 run the original machine code in a JS x86, and the music is the original 28-channel module.

The original

DOPE.EXE (584,133 bytes) by Complex: code jmagic, graphics and music jugi, boxes pixelled by reward. It wants 550k of base memory, 600k of extended memory and a Gravis UltraSound with 512k: the music is a 28-channel ProTracker module mixed by the GUS hardware, not by the CPU. The readme admits the end scroll was never made.

Aspect ratio

The demo runs in VGA mode 13h: 320×200 pixels on a monitor that was 4:3. Pixels were therefore 1.2× taller than wide. The screenshots above are 320×200 and are shown at 4:3 here; the player does the same with CSS (aspect-ratio: 4/3) and nearest-neighbour scaling. The button toggles to the raw 16:10 shape if you want to see the difference.

How it plays here

Every part runs as JavaScript written from the original's machine code, not as a recording and not through an emulator. Part 1 (the first 39 s, the "COMPLEX" logo) is transcoded: its picture and palette tables are read out of the unpacked block and the frames are written directly. Parts 2 to 7 are ports (web/js/ports/): the page unpacks the blocks out of DOPE.EXE, loads each into a 1 MB memory image the way the original loader did, and runs the port, which reads the demo's own tables, pictures and scripts from that image and draws the frames. Each port was checked against the original's code, running in an x86 emulator, byte for byte, frame by frame (next section), so the pictures are the demo's own.

  1. The loader. Each part is mapped at segment 0xf8b and 23-28 words are relocated (+0xf7b). The relocation lists are not in the file as far as I could find; they were measured by diffing a DOSBox-X memory snapshot of every part at its start against its block (tools/blocksnap.py, tools/relocdiff.py, data in web/data/parts.json). The ports use the same image and the same rule (seg()).
  2. The clock. A part's whole animation hangs on its own INT 8 handler at the monitor's 70 Hz. The page drives each port from the audio clock (70.086 ticks per second), so the animation keeps the original's speed. Each part lasts a fixed number of ticks (measured: 8200, 3665, 7443, 4557, 4063, 2494), which makes the whole demo 7:53.
  3. Pause and seek. Pause stops the clock. Seek moves the port's clock to the new tick (parts 4 to 6 start from the end of the part before, which the worker computes by running that port to its end) (the part's counters, the objects' positions and the lighting tables all follow the tick, so this is instant) and draws one frame; a few effects that remember the previous frames (the glow of part 2, the lights of part 6) settle in the next few frames.
  4. Speed. A frame of part 3 is a few thousand polygons through plain JavaScript typed arrays; the page draws 40 to 60 pictures a second in headless Chrome, and the status line under the player shows the number live. (Before the ports the same parts ran through an interpreter and a dynamic recompiler at 30 to 40; both are still in the repository because they are the oracle.)

Real ports

Running the original code is the fast way to a faithful demo; the goal here is also to understand how it was made, so every part was rewritten as JavaScript (web/js/ports/), one at a time. A port is accepted only when it reproduces the original byte for byte, on real data: each routine is run in the emulator on a copy of the machine and compared with the port function (tests/test_port*.mjs), and the whole part runs in lock step with the original, frame by frame, with the timer interrupt held back so a frame is never interrupted. The method is in the porting method; each part has its own study.

The process

  1. Look at the file. A DOS MZ header, then eight Rob Northen RNC (ProPack method 1) blocks found by scanning for RNC\x01. Block 0 (25,570 bytes unpacked) is a DPMI extender plus a GUS player: Oskari Tammelin's ProTracker for GUS, patched to upload samples into GUS RAM. Blocks 1..7 are the demo parts, loaded one at a time as overlays.
  2. Unpack. tools/rnc.py (and the identical web/js/rnc.js) decompress all eight blocks; the CRCs stored in each header match.
  3. Disassemble. With ndisasm. The first guess (32-bit protected mode) was wrong: the parts are 16-bit real-mode code that uses 32-bit registers, and part 1 reprograms VGA mode 13h into a planar layout.
  4. Get ground truth. tools/refcapture.py boots the real DOPE.EXE in DOSBox-X with GUS emulation and saves 320×200 frames, optionally tagged with the part's counter read out of guest memory. tools/blocksnap.py watches the INT 8 vector to snapshot every part at the moment it starts.
  5. Transcode part 1. Once the picture layout (the card's planes read back four pixels per byte, CRTC start/offset counted in plane bytes) and the timer were right, part 1 reduced to a window into the unpacked picture plus two palette ramps (web/js/part1.js): 11 of 15 reference frames are byte-identical, 4 differ by 8 pixels each.
  6. Run the original to measure it. A small x86 interpreter and VGA model (tools/vm/) first served as a measuring rig, then played parts 2 to 7 for a while, and is now the oracle: the original's own code, runnable one routine at a time. The reversing it needed was the loader, the entry points, the timer model, and what the card has to do (reads of A0000 as well as writes: block 5 repaints over the checker block 4 left on screen).
  7. Check the interpreter against a real x86 model. tools/difftrace2.mjs dumps a whole run and tools/diffcheck2.py replays the interpreter's trace in Unicorn (QEMU's CPU) instruction by instruction, comparing registers, flags and every store, feeding it the same port reads and interrupts. It found, one at a time: shld/shrd with an immediate count executed as byte operations (the texture mapper's coordinate packing, which is why the first discs looked like moiré), rotates clobbering ZF/SF/PF, imul never setting CF/OF, and string instructions stepping SI/DI as 32-bit registers (a rep movsd across 64 KB, which hung part 6).
  8. Port, one part at a time, against the oracle. Rewrite a routine in JavaScript; run the original routine on a copy of the machine and the port on the same data; compare every byte it can write; then run the whole part from its first instruction beside the port, the timer held back so a frame is never interrupted, and compare variables, buffers, palette and picture after every frame (the method). A polygon-by-polygon mode finds the first bad triangle. Part 4 went first, then 3 with the shared engine, then 7, 5, 6 and 2.
  9. Notice the engine is one engine. Parts 2, 3, 5, 6 and 7 turned out to be five assemblies of the same source. Disassembling two copies and diffing them with the addresses blanked out showed part 7's differs from part 3's in two lines; the differences between the others are the history of the author's changes (a rounded matrix, a phong index scaled by 8, 9 or 10, a lighting table that starts to move). The engine.
  10. The music. DOPE.MOD is a 28-channel ProTracker module that the demo's GUS driver plays. The page plays it with libopenmpt compiled to WebAssembly (web/vendor/, web/js/openmpt.js): 8 tap windowed-sinc interpolation, full stereo separation, rendered at the sound card's own rate. The song clock is the number of audio frames rendered, which is what every picture follows, and a seek is libopenmpt's own (it replays the song state up to the nearest row, tests/test_openmpt.mjs). An earlier replayer of my own (a 28 channel mixer, loudness envelope correlation 0.88 against libopenmpt over the whole tune, a 0.3 s clock drift) was replaced by it.

Everything is in the repository: docs/ANALYSIS.md and docs/RUNTIME.md hold the notes and measurements, docs/PORTING.md the method, docs/ENGINE.md and docs/PORT*.md what each part turned out to be, the effects what each part shows and the seven 3D models.
